修改内容：由AI辅助执行逐份填写、提交和统计检查，保存提交结果与最终统计截图。

结果复核：[完整执行记录](evidence/phase2/phase2-complete-browser-20261027-01/执行记录.md)、[总览截图](evidence/phase2/phase2-complete-browser-20261027-01/text-overview-statistics.png)及[单版截图](evidence/phase2/phase2-complete-browser-20261027-01/text-v2-statistics.png)。

## 六、AI使用说明

### 6.1 AI帮了什么

AI主要帮助我把需求分析转化为可以运行和检查的实现。第一阶段的题目属于单份问卷，第二阶段又要求共享、历史和跨问卷统计，修改会同时影响数据库、后端和页面。我先限定保留的结构和数据，再让Codex梳理原有ID引用、比较复用方案，并按数据结构、版本、分享、统计、页面和验收分步推进，避免一次性修改后无法判断问题来源。

| 环节 | AI完成的工作 | 对应产出 |
| --- | --- | --- |
| 基线与模型分析 | 阅读原集合、接口和答卷引用，协助比较复制、共享引用和版本快照的影响，制作备份并核对哈希 | 第01—03项，第一阶段基线与增量模型 |
| 数据库与后端 | 实现新增集合校验器、索引、题库与版本服务、分享与选题、来源检查、使用追踪和统计接口 | schema.py、library.py、sharing.py、library_statistics.py及路由 |
| 前端接入 | 实现题库、版本详情、分享、草稿选题及统计展示，处理来源提示、确认与错误反馈 | LibraryPage.vue、LibraryQuestionPage.vue、LibraryPicker.vue及原编辑页改动 |
| 验证与问题修正 | 编写自动测试，运行隔离MongoDB回归，核对旧记录，并通过浏览器完成多账号填写和结果检查 | P2-01—P2-21、浏览器记录、提交结果与统计截图 |

主要程序和自动测试由Codex实现。我负责确认任务边界、提出业务选择和遗漏、检查手工页面结果；多账号重复填写由AI辅助执行。AI减少了重复编码和测试准备工作，但它的完成说明还需要与需求、实际页面和保存的数据核对。最新完整回归为[后端109项、前端12项通过](evidence/phase2/regression-20261028/README.md)，其余证据按各项任务分别记录。

### 6.2 AI做错了什么

AI的主要问题是初版覆盖不充分，以及接口逻辑与实际操作没有完全衔接。代码能运行、测试能通过，并不说明用户的完整任务已经实现。

| 发现的问题 | 为什么需要修改 | 处理与验证 |
| --- | --- | --- |
| 数字题只有平均值 | 平均值不能回答需求示例中的年龄总体分布，结果缺少用户关心的分布情况 | 我要求补充区间分布；AI修改服务和页面。两卷各五份22和42得到均值32、两个非零区间各5；追加70后验证稀疏区间抑制 |
| 题库管理与复用入口不完整 | 仅能创建和选用，不能充分支持改名、移除及把已有问卷题保存供以后使用 | 我逐条核对第1、7类需求后要求补齐，增加改名、归档和旧题保存接口及页面；P2-17、P2-18、P2-21检查结果 |
| 来源提示遮蔽编辑表单、确认框无法可靠操作 | 来源题虽然可以读取，实际却不能顺利修改或完成确认；接口测试难以发现这类渲染问题 | 浏览器验收定位到条件渲染互斥，AI调整显示条件和页面内确认，复测改题后来源脱离、仅改跳转时来源保留 |
| 误选题后缺少删除入口 | 用户无法纠正草稿中的选题错误，完整编辑流程被中断 | 我在手工操作中发现并要求补充；删除仅限本人草稿实例，后端拒绝发布后、越权和被跳转引用的删除，页面确认与取消均检查 |

统计范围还有一次明确的需求取舍：早期实现要求问卷所有者逐卷授权，后续我确认“所有有效同版问卷自动纳入”，同时限制作者只能读取聚合结果。AI据此调整接口和页面，保留早期授权接口用于兼容。这一变化属于需求口径迭代，与表中的功能遗漏和页面缺陷分别记录。

### 6.3 自己改了什么

我首先修改了任务的推进方式：要求先盘点和备份，按依赖分单元实施，每次说明改动范围、实际测试结果和未验证边界，而不是仅接受“功能完成”的描述。对“真实库测试未启用”，我追问其含义，要求区分跳过与通过，并补上真实MongoDB校验器、索引和重复初始化检查。

业务上，我对照八类需求追问缺项，推动补充年龄分布、题库改名与移除、旧题保存和草稿删除。我还明确了自动汇总的范围、同内容版本合并规则和文本展示门槛，使后端统计、前端说明和测试使用同一口径。这些修改由我提出和确认，具体代码由Codex落实。

页面验收中，我亲自完成题库改名、版本创建与恢复、条目版本切换、分享选题、发布和撤销，并保存截图。我检查的是操作之间的关系：作者从版本2生成版本5后，已发布问卷仍保留版本1，已有草稿仍保留版本2；撤销分享后新草稿不能继续选题，先前两份问卷的实例仍存在。这样既核对了操作成功，也核对了修改没有影响已有内容。对应证据见[本人手工截图](images/phase2-manual/README.md)及[阶段二测试用例](phase2-test-cases.md)。

数字与文本的多账号填写由AI辅助完成，我要求逐份从正常页面提交并记录结果，以补足只有合成数据截图的不足。数字十份答卷和文本十六份答卷分别核对输入、提交和最终统计，不能把页面能显示结果直接当作填写链路已经验证。

### 6.4 自己设计了什么

我参与的设计主要是数据边界和业务规则的确定。数据模型是在与AI讨论后采用的方案，具体预占状态、条件更新和并发代码由Codex实现；我据此检查方案是否符合需求，而不是将全部实现归为本人独立编写。

题目身份与历史保留。我确认将“逻辑题目—内容版本—问卷实例—答卷”分开组织。仅复制文字无法识别同题，直接共享可修改内容又会改变旧问卷。因此逻辑题目提供共同身份，版本保存完整历史，问卷实例复制选用时的快照，旧答卷继续引用原实例ID。这个选择接受一定内容冗余，换取历史可解释性和旧流程兼容；旧题不按相似题干自动合并。

版本变化与问卷配置的边界。恢复旧内容生成新版本，题库条目固定所选版本，避免新版本自动替换用户原先的选择。题序和跳转目标仍属于具体问卷，不放进共享版本，因为另一份问卷的目标题目ID在本卷中没有意义。草稿改写题干、选项或校验后脱离来源，仅改本卷跳转时保留来源，防止不同内容被混入同版统计。

MongoDB的嵌入与引用。选项和校验随完整题目一起读取，适合嵌入版本；版本历史、题库条目和分享关系独立增长且有不同查询入口，采用集合与ID引用，避免单文档持续扩大。校验器检查类型和必要字段，唯一索引防止重复版本号、关系和请求标识，版本归属与快照一致性由后端检查。我以这些职责是否分清作为核对依据，不把字段类型合法等同于业务关系正确。

分享权限与统计范围。我区分题目作者、获分享者和问卷所有者：分享允许查看和选用，不允许代作者改版本或读取他人答卷。对“所有问卷”，我选择自动纳入有效来源实例，只向题目作者提供聚合；撤销分享只限制以后的选题，不删除已保存快照。这样兼顾跨用户复用、统计覆盖与原问卷所有权。

统计对象与结果保护。我确认不同内容版本分别展示，只合并完整内容相同的版本，避免混合不同题意。同一答卷内重复放置同版题目时按答卷去重；数字先求卷内平均，再让答卷等权汇总，避免题目重复次数改变权重。文本仅展示达到人数门槛的重复答案，并保留小样本抑制。参与问卷数、答卷数与不同填写者人数分别解释，原单卷统计继续区分未到达、到达留空和有效回答。

这些选择最终落实到集合、接口、页面和测试。我通过版本5与原问卷对照、分享撤销后的实例保留、数字均值与分布、文本分组等结果核对设计。当前验证面向单服务实例；并发协调实现与异常恢复仍按实际部署条件说明，小样本规则也不作为完全匿名保证。
