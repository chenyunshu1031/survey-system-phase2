# 第二阶段系统与数据库设计

## 一、系统目标与扩展范围

本阶段在原Vue3、TypeScript、FastAPI和MongoDB问卷系统上扩展题目管理。原账号、问卷创建发布、四种题型、跳转、填写校验、答卷保存和单问卷统计继续使用；新增常用题保存、个人题库、版本历史与恢复、指定用户分享、固定版本选题、使用追踪和跨问卷汇总。

前端调用/api/v1，不直接读写数据库。后端按资源检查权限与状态，执行版本和来源校验；MongoDB保存业务文档，通过集合校验器和索引约束基础结构。第一阶段核心流程的详细说明见[原系统设计](design.md)，接口见[API说明](api.md)。

## 二、数据模型与第一阶段兼容

| 数据层 | 集合 | 职责 |
| --- | --- | --- |
| 原系统 | users、surveys、questions、responses | 保留账号、问卷、题目实例与答卷，以及原ID和引用 |
| 逻辑题目 | libraryQuestions | 稳定身份、所有者、当前版本指针和版本计数 |
| 内容版本 | questionVersions | 完整内容、versionNo、parentVersionId，已提交内容不原位覆盖 |
| 个人题库 | questionBanks、questionBankItems | 题库名称、归档状态和固定选定版本 |
| 分享 | questionShares | 指定接收者及撤销状态，控制查看与选用 |
| 早期授权统计 | crossSurveyConsents | 保存阶段二早期实现的授权记录，兼容相应接口；不决定当前自动汇总范围 |

questions继续表示问卷内独立题目，只新增可选的sourceLibraryQuestionId和sourceVersionId。选题复制所选版本的题型、题干、选项及其ID、必答和校验，生成新的实例ID；order和jumpRules属于当前问卷，选入时不复制其他问卷的规则。responses继续引用实例，不因逻辑题目升级而改写。

以下为引用关系的结构示例，L、V1和QA代指相应ObjectId：

```javascript
// questionVersions：完整版本内容与来源链
{ _id: V1, libraryQuestionId: L, versionNo: 1, parentVersionId: null,
  type: "number", title: "你的年龄", required: false,
  options: [], validation: { minValue: 0, maxValue: 120 } }

// questions：选入一份问卷后的独立实例，复制完整内容
{ _id: QA, surveyId: S, order: 1,
  sourceLibraryQuestionId: L, sourceVersionId: V1,
  type: "number", title: "你的年龄", required: false,
  options: [], validation: { minValue: 0, maxValue: 120 }, jumpRules: [] }
```

旧题缺少来源字段仍可读取，不按题干相似度自动合并。所有者可显式保存旧题供以后选用，但原实例和历史答卷不追溯归入新逻辑题目。schemaVersion是文档结构版本，versionNo是题目内容版本，configurationRevision和submissionRevision是内部操作修订号，三者用途不同。

## 三、MongoDB建模理由

选项与校验参数决定版本含义，通常随完整题目一起读取，因此嵌入版本文档。历史版本、题库条目和分享关系有独立查询方向且持续增长，采用独立集合及ID引用，避免单文档无限扩大。问卷实例复制内容形成有意冗余，代价是额外存储，收益是固定历史内容并继续使用原填写流程，不随最新版本同步。

关系数据库也能实现这些功能，并在外键和多表事务上有优势。本项目使用MongoDB，既满足课程要求，也延续既有文档模型；嵌套选项、题型校验和答卷可以按完整内容读写。系统接受跨集合关系由后端复核、跨文档写入需要额外协调的成本，不将所有实体机械地放入一个集合，也不为旧数据引入整体迁移。

| 访问与约束 | 索引或检查 |
| --- | --- |
| 查询个人题目和题库 | ownerId、createdAt、_id复合索引 |
| 同题版本号唯一 | libraryQuestionId、versionNo唯一索引 |
| 创建重试不重复写入 | 所有者与创建请求键、题目与版本请求键等唯一索引 |
| 固定题库条目和分享关系 | bankId＋libraryQuestionId、libraryQuestionId＋recipientUserId唯一索引 |
| 接收者反查分享 | recipientUserId、libraryQuestionId索引 |
| 使用追踪和同版统计 | sourceLibraryQuestionId、sourceVersionId、surveyId部分索引 |

完整校验器与索引定义见[MongoDB schema](../backend/app/db/schema.py)。$jsonSchema约束必要字段、类型和枚举，来源字段同时缺失或成对为ObjectId；版本归属、资源权限及快照一致性由后端检查。题干、选项、校验与跳转配置存于文档，程序解释operator和priority等规则，不对个别问卷硬编码。

## 四、版本、题库与分享逻辑

创建逻辑题目形成首版；需要修改时，从指定已提交版本创建新版并记录parentVersionId。恢复旧内容也新增版本，不覆盖旧版或后续历史。不同问卷可同时选用不同版本；题库条目保存selectedVersionId，用户明确切换后才更新，不自动跟随当前版本。

题库支持创建、改名、归档；加入、切换和移除条目不删除原题与版本。分享由作者按用户名授权；接收者可查看已提交版本并选入本人草稿，不能修改原作者版本、管理作者题库或读取他人原始答卷。撤销只阻止今后选题，已有实例保持不变。使用追踪显示问卷ID、实例ID、版本和状态等必要关联信息。

草稿改写题目内容后清除两个来源字段，仅改本卷跳转时保留来源。发布前复核来源快照及原有规则，发布后锁定题目。误选题可以从本人草稿中删除，仅移除当前实例；已发布、越权或被其他跳转引用时拒绝删除。

## 五、跳转、填写校验和答卷保存

原jumpRules继续使用本卷题目与选项ID，按priority选择首条命中规则，否则顺序进入下一题；目标必须在当前题之后，避免回环。文本题不配置条件跳转。共享版本不携带问卷专属跳转目标。

后端在配置、发布和提交三个阶段检查题型、选项、数值、字数、必答及规则引用。提交时从第一题重建路径，拒绝漏题、错误顺序或提交被跳过题。通过校验后一次保存有效answers和完整visitedQuestionIds；原部分唯一索引继续限制禁止重复填写的问卷。匿名设置控制展示身份，不取消登录与后端重复检查。

## 六、跨问卷统计

当前自动接口纳入所有用户问卷中来源ID、版本归属和内容快照有效的实例，仅逻辑题目作者可读聚合值。无来源旧题不自动识别为同题。分享撤销不删除已保存来源，也不改变其统计归属。

同一答卷内出现多个同版实例时，答卷、到达和回答最多各计一次。数字题先计算答卷内同版有效值均值，再按答卷等权计算总体均值和自适应区间分布。文本按重复答案计频次，至少五名不同填写者给出同一文本才展示。总览仅合并题型、题干、必答、选项及其ID和校验完全相同的版本；不同内容分组。

非零答卷计数、选项或数字区间的不同填写者不足五人时，抑制答卷层面结果并返回样本不足状态；不返回他人原始答卷或身份。参与问卷数可含有有效来源但没有答卷的草稿。小样本抑制降低直接暴露，对跨时间差分推断仍有局限。

原单问卷统计继续按实例ID、访问路径和有效答案计算，由问卷所有者查看，不被新汇总口径替换。阶段二早期按问卷授权的统计接口保留用于兼容，与当前自动接口分别标明范围。

## 七、一致性与适用范围

当前MongoDB采用standalone部署，版本创建通过逻辑题目预占、单文档条件更新、唯一索引和请求键协调。请求键标识一次操作，指纹检查同键重试内容是否一致；不同内容争用或状态变化返回409。中断后可带原键重试，请求标识丢失时需核查预占状态后恢复。

分享记录登记进行中的选题，撤销与活动选题冲突时返回409。问卷配置写入、发布、关闭和提交继续使用原活动计数与修订号。统计前后检查提交活动和submissionRevision，变化则返回409，页面清除旧结果并提示刷新。这些机制面向单服务实例，不替代多实例事务或跨实例协调。
